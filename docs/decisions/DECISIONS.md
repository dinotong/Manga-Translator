**เพื่อประหยัด “คำขอ” ซึ่งการวัดบอกว่าตอนนี้ไม่ได้ขาดแคลน** (`backoff=0` · pacing ~2 วิ)

> D-043 สรุปไว้เองว่า **batching ซื้อ “คำขอต่อหน้า” ไม่ใช่ throughput** · 2 หน้าต่อคำขอก็**ลดจำนวนคำขอลงครึ่งหนึ่งแล้ว** ซึ่งคือประโยชน์ทั้งหมดที่มันให้ได้

### 🔴 บั๊กจริงที่ `lingered=3011ms` เปิดโปง — ไฟล์นั้นสัญญาไว้เอง แล้วโค้ดทำผิดสัญญา

เป็น pure + export + มีเทสต์ 3 ข้อ **เพื่อให้ invariant นั้นเป็นสิ่งที่ตรวจได้ ไม่ใช่สิ่งที่กล่าวอ้าง** — มันถูกกล่าวอ้างมาแล้ว และการวัดจับได้ว่าผิด

**ย้อนกลับ:** `remainingLinger` กลับไปใช้ `BATCH_LINGER_MS` เต็มได้ · log ลบได้ทั้งชุด

## D-043 · **หน้าต่างรวม batch สั้นกว่าจังหวะที่หน้ามาถึง** — เลย “รอจนครบเวลาแล้วออกไปหน้าเดียว” ทุกครั้ง
**2026-08-16 · `core/prefetch.ts`, `background/read-batcher.ts`, `background/read-batcher.test.ts` (ใหม่), `entrypoints/content.ts`**

### เวลาไปไหน — วัดแล้ว ชัดเจน ไม่ต้องเถียง

```
acquire= 88ms detect=116ms read= 2819ms total= 3024ms
acquire=188ms detect=235ms read=23694ms total=24119ms
acquire= 76ms detect=332ms read=50223ms total=50633ms
```

**`read` คือทั้งหมด** · `acquire + detect` รวมกัน 0.2–1.0 วิ ไม่เคยสำคัญ · และ `read` ไม่ได้แค่ช้า มัน**เหวี่ยง**: 2.8 → 50.2 วิ

```
key wait: paced=2587ms backoff=0ms upstream=1814ms
```

`backoff=0` → **ไม่โดนลงโทษเรื่อง rate limit เลย** · pacing ของเราเอง ~2 วิ · เทียบกับ `wire=49517ms` → **ที่เหลือคือ Google ล้วนๆ**

### 🔴 เกือบทุกคำขอออกไปแค่ **1 หน้า** ทั้งที่รอจนหมดเวลา

```
request done: 1 page(s), 1 crops, lingered=713ms wire= 2106ms
request done: 2 page(s), 2 crops, lingered=707ms wire=26298ms
request done: 1 page(s), 2 crops, lingered=705ms wire=49517ms
```

`lingered ≈ 705ms` คงที่ = **หน้าต่างหมดเวลาเสมอ** แล้วออกไปหน้าเดียว

**สาเหตุ:** `BATCH_LINGER_MS = 700` ถูกตั้งจาก**ขอบล่างที่ถูก** (detect 126–481 ms แบบ serialise → ต่ำกว่า 500 ms ไม่มีทางเจอใครเลย)
แต่**ขอบล่างไม่ใช่ขนาด** · เลขที่หายไปคือ**จังหวะที่หน้ามาถึง**:

หน้า speculative ถูกเว้นด้วย `MIN_PREFETCH_GAP_MS = 500` (มารยาทต่อ image host — **ห้ามแตะ**) และเช็คบน tick ทุก `250 ms`
→ **มาถึงชิดกันที่สุดได้ 750 ms**

> หน้าต่าง 700 ms จึง**สั้นกว่าช่วงห่างหนึ่งช่วงพอดี** → จับได้ 0 หน้าเป็นปกติ · จับได้ 1 บ้างตอนจังหวะเหลื่อม · **จับ 2 ไม่ได้เลย**
> ทุกบรรทัดที่วัดมาอธิบายได้ด้วยข้อนี้ข้อเดียว

**แก้:** `BATCH_LINGER_MS = (MAX_PAGES_PER_REQUEST - 1) × SPECULATIVE_ARRIVAL_GAP_MS` = 2 × 750 = **1500 ms**
คือ**เวลาที่น้อยที่สุดที่ batch เต็มจะประกอบตัวได้จริง** · ย้าย `PREFETCH_TICK_MS` เข้า `core/prefetch.ts` เพื่อให้เลขนี้มีนิยามเดียว → ค่าคงที่ 3 ตัวดริฟต์ออกจากกันอีกไม่ได้
มีเทสต์คุมความสัมพันธ์นี้ 3 ข้อ เพราะ**ไม่มีอะไรใน type system รู้ตัวเมื่อเลขใดเลขหนึ่งขยับ**

**ราคา:** หน้า lookahead รอเพิ่มไม่เกิน 1.5 วิ เทียบกับคำขอ 2.8–50 วิ และ lead 12 วิของ IntersectionObserver = เศษ · **หน้าที่คนอ่านมองอยู่ไม่เคยรอ timer นี้** (foreground/manual ออกทันทีและลากคนที่รออยู่ไปด้วย)

### 🔴 แก้คำกล่าวอ้างในหัวไฟล์ที่ทำให้เข้าใจผิด — “3 หน้าต่อคำขอ = throughput 3 เท่า”

ประโยคนั้นเคย**จริง**ตอนงานยังเป็น serial และ 1 job = 1 request · **ตอนนี้ไม่จริงแล้ว และมันหลอกคนอ่าน log ไปแล้ว 1 ราย**

เพดาน concurrency นับเป็น**หน้า ไม่ใช่คำขอ** (`speculativeAllowance`) → หน้าเสร็จที่อัตรา **หน้าที่วิ่งอยู่ ÷ round trip**
**การยัดหน้าเดิมลงในคำขอที่น้อยลง ไม่เปลี่ยนทั้งตัวตั้งและตัวหาร**

สิ่งที่ batching ซื้อจริงคือ **คำขอต่อหน้า** → คือ**เพดานหน้าจะขึ้นได้สูงแค่ไหนก่อนโควตาต่อนาทีจะเป็นตัวบีบ**
7 หน้าแบบหน้าละคำขอ = 7 คำขอ · 7 หน้าอัด 3 ต่อคำขอ = 2–3 คำขอ · **ผลต่างนั้นคือสิ่งที่ทำให้ขึ้นเพดานหน้าได้โดยไม่พัง**

> **batching ไม่ใช่คันโยก throughput — มันคือสิ่งที่ทำให้คันโยก throughput ใช้ได้** และต้องทำงานก่อนถึงจะขึ้นเพดานได้อย่างปลอดภัย

**ลำดับที่ถูกคือ:** แก้ batching (รอบนี้) → ยืนยันจาก `request done:` ว่าได้ 3 หน้าจริง → **ค่อย**ขึ้นเพดานหน้า → วัด

### สมมติฐาน “งานถูกทิ้ง” ของ D-042 — **ยังไม่ถูกหักล้าง**

`killed=0` `adopted=1` ในการอ่านรอบนี้ **ไม่ได้แปลว่าสมมติฐานผิด** — แกลเลอรีนี้ `NO_TEXT_FOUND` สูงถึง 22 หน้า
คนอ่าน**ไม่เคยตามมาทัน เพราะแทบไม่มีอะไรให้ตาม** · `lead=6` ที่เห็นคือหน้าที่ไม่มีบทพูด (ซึ่งนับเป็น ready ถูกแล้ว แต่**ไม่ใช่ระยะนำที่มีความหมาย**)
→ ต้องทดสอบบนแกลเลอรีที่ข้อความแน่น เช่น **1718710**

**และนี่คือข้อจำกัดของ `lead` ที่ต้องบันทึกไว้:** หน้าไร้บทพูดทำให้ `lead` ดูดีโดยไม่ได้แปลว่าคนอ่านได้อะไร

## D-042 · **การขึ้นเพดานของ D-041 ไม่ได้ผล** — และตัวเลขในการวัดนั้นเองชี้ว่า **งานถูกเริ่มแล้วโยนทิ้ง** ไม่ใช่ช้า
**2026-08-16 · `background/pipeline.ts`, `background/read-batcher.ts`, `translation/KeyRing.ts`, `entrypoints/content.ts`**

> 🟡 **รอบนี้ไม่แก้พฤติกรรมอะไรเลย** — เป็นการวัดล้วนๆ ตามที่ coordinator สั่ง

### ผลวัด 7 heartbeat ติดกัน · แกลเลอรีเย็น 25 หน้า · เปลี่ยนหน้าทุก 4 วิ

`lead` ตลอดการอ่าน: **`0, 1, 0, 0, 0, 0, 0`** · `jobs=0/8` `speculative=7/7` → migration ถึง runtime แล้วจริง

**ยอมรับตรงๆ: D-041 ไม่ได้ผล** · `started` เดินจาก 9 → 24 ใน 90 วิ = **1 หน้าทุก ~6 วิ ซึ่งเท่ากับตอนที่ allowance ยังเป็น 3 เป๊ะ**
ให้วิ่งพร้อมกันได้ 7 แทน 3 แล้ว**ไม่ได้หน้าเสร็จเพิ่มเลย** → เพดานไม่เคยเป็นตัวจำกัด

### 🔴 เลขในการวัดนั้น**ปิดบัญชีได้พอดี** และมันไม่ได้บอกว่า “ช้า”

heartbeat สุดท้ายที่ยังอ่านอยู่: `started=24` · `adopted=18` · `failed=3` · `ready=2`

```
18 (adopted) + 3 (failed) + 2 (ready) + 1 (กำลังวิ่ง) = 24 = started
```

`adopt()` ล้าง `speculative` แต่**ไม่แตะ `page`** และ RESULT เขียน `prefetchReady.add(job.page)` สำหรับทุก job ที่ `page !== null`
→ **ถ้า 18 งานที่ถูก adopt ทำสำเร็จ `ready` ต้องขึ้นไปราว 18 · มันค้างอยู่ที่ 2**

> **18 งานถูก adopt · 0 งานทำเสร็จ**

### เส้นทางที่อ่านเจอในโค้ด (สมมติฐาน ยังไม่พิสูจน์)

```ts
function detach(img, job) {
  job.imgs.delete(img);
  if (job.imgs.size === 0 && !job.speculative) cancel(job);   // ← ตรงนี้
}
function adopt(job, img) { job.speculative = false; ... }      // ← ถอดเกราะออก
```

1. prefetch เริ่มหน้า N → `speculative = true` → **`detach` ยกเว้นให้ ไม่ฆ่า**
2. คนอ่านมาถึงหน้า N ตอนงานยังไม่เสร็จ → `adopt()` → `speculative = false` → **เกราะหายไป**
3. อีก 4 วิคนอ่านเปลี่ยนไปหน้า N+1 → `detach` → `imgs.size === 0 && !speculative` → **`cancel()`**

**การ adopt ถอดสิ่งที่ปกป้องงานนั้นอยู่ออก แล้วการเปลี่ยนหน้าครั้งถัดไปก็ฆ่ามัน**
→ detect + Gemini ของ 18 หน้า ถูกเริ่มแล้วทิ้ง · เป็น**สายพานที่หมุนเปล่า** ซึ่งอธิบายว่าทำไมขึ้นเพดานแล้วไม่ขยับ (ได้งานคู่ขนานเพิ่ม แต่อัตราการทิ้งเท่าเดิม)

กฎ “คนอ่านไปแล้ว = ยกเลิก” (D-024) ถูกสำหรับงานที่มาจาก element · แต่ `read-batcher` เขียนไว้เองว่าเมื่อคำขอออกสายไปแล้ว **ไม่มี abort และคำตอบถูกแคชอยู่ดี** → ยกเลิกตอนนั้น**ไม่ได้ประหยัดอะไร แค่ทิ้งคำตอบที่จ่ายเงินไปแล้ว**

| `KeyRing.ts` | `key wait: paced=… backoff=… upstream=…` | **pacing ของเราเอง** vs **latency ของ Google** |
| `content.ts` | `killed=` ใน heartbeat | **งานที่จ่ายไปแล้วถูกทิ้งกี่ครั้ง** |

`killed` แยกจาก `adopted` เพราะ**มันคืองานเดียวกันคนละจังหวะ** และผลต่างของสองตัวนี้คือคำตอบทั้งหมด
`read = lingered + paced + backoff + upstream` → เหลือเศษเท่าไรคือ latency ฝั่งโน้นล้วนๆ

### `PROVIDER_BUSY=3` จาก 24 — ไม่ใช่เศษทิ้ง

503 กิน **3 ใน 24** งานใน 90 วิ และเห็นในการอ่าน 2 รอบก่อนหน้าด้วย · `PROVIDER_BUSY` ของ D-040 ทำให้มันนับได้แล้ว **ยังไม่ retry** — ดูตัวเลขจาก instrument ก่อนค่อยตัดสิน

### 🔴 สิ่งที่ต้องพูดกับเจ้าของตรงๆ ถ้าผลออกมาเป็นแบบนั้น

**ถ้าท่อส่งหน้าได้ช้ากว่าที่คนอ่านเปิดหน้า ไม่มีค่า lookahead ไหนและไม่มีเพดาน concurrency ไหนสร้างระยะนำได้เลย**

### 🔴 `jobs=0/4` ไม่ได้แปลว่า “มีสล็อตว่าง 3 อัน” — และนี่คือจุดที่พลิกคำตอบ

> **ไม่มี “concurrency ว่าง” ให้ speculation ใช้เลย** — คำขอของ coordinator ว่า “ให้ speculative ใช้สล็อตว่าง” ถ้าทำตามตรงๆ จะเป็น **no-op ที่หน้าตาเหมือนการแก้**

### 🔴 เพดานสองอันบังเอิญเท่ากันที่ 3 → เลยบังหน้ากันเอง

| ที่ไหน | สูตร | ค่าตอน `maxInFlight=4` |
|---|---|---|
| SW `canAdmit` | `total < cap - 1` | **3** |
| content `prefetchRefusal` | `inFlight < batchSize` = `MAX_PAGES_PER_REQUEST` | **3** |

อันล่าง**ไม่เกี่ยวอะไรกับ concurrency เลย** มันคือขนาด batch · ที่งบ 4 มันบังเอิญเป็นเลขเดียวกัน **ความผิดเลยมองไม่เห็น**

`cap = 1` → allowance **0** (ไม่ใช่ 1) — มีสล็อตเดียวจะกันอะไรไม่ได้ ต้องไม่เดาเลย · `prefetchRefusal` เลิก floor ที่ 1

### 🔴 เหตุผลของ `DEFAULT_MAX_IN_FLIGHT = 4` **หมดอายุไปแล้ว** — เป็นครั้งที่ 3 ของโปรเจกต์นี้

→ ตอนนี้ `prefetchRefusal()` คืน**ชื่อเงื่อนไขที่ปฏิเสธ** · content script นับแล้ว log ทุก 15 วินาที · **ครั้งหน้าจะเป็นการวัด ไม่ใช่การเถียง**

อ่านโค้ดแล้ว **ตัดออกไม่ได้ 2 ข้อ และตัดออกได้ 2 ข้อ**:

- ❌ *ไม่จริง* — “`foregroundWaiting` ปิด prefetch ตลอดช่วง 18 วินาทีของ job” · มันคือ `queue.length > 0` และ `pump()` ส่งงานออกทันทีที่มีสล็อตว่าง จึงเป็น true แค่ชั่วขณะ
- ❌ *ไม่จริง* — “speculative job ค้างใน `active`” · `settle()` ลบทิ้งทั้งตอนสำเร็จและตอนพัง
- ⚠️ *เป็นไปได้สูง* — **throughput ต่างหากที่จำกัด**: speculative 3 หน้าพร้อมกัน × round trip เฉลี่ย 18 วิ ≈ ได้ 1 หน้าทุก 6 วิ ขณะที่คนอ่านเปิดหน้าใหม่ทุก 3–4 วิ → ระยะนำถูกกินหมดเสมอไม่ว่าตั้งลึกแค่ไหน
- ⚠️ *เป็นไปได้* — **`MAX_CONSECUTIVE_MISSES = 2`** · imhentai มีนามสกุลไฟล์ปนกันในแกลเลอรีเดียว ถ้าเดา URL พลาด 2 ครั้งติด prefetch จะ**ปิดทั้งแกลเลอรี** ซึ่งจากมุมคนอ่านหน้าตาเหมือนกันเป๊ะ

**ค่า default ของ `prefetchLookahead` 3 → 10** (`DEFAULT_LOOKAHEAD`) · 🟡 **ไม่ใช่การแก้อาการข้างบน** เจ้าของตั้งสูงสุดอยู่แล้วและยังเจอ
เหตุผลคือ 3 หน้า = ระยะนำไม่ถึง 20 วินาที และ “ต้องรำคาญก่อนถึงจะไปเจอว่ามีสวิตช์นี้” ไม่ใช่การออกแบบที่ดี · **เป็นการใช้ดุลพินิจ ไม่ใช่การวัด** — ไม่มี fixture ไหนตัดสินได้ ต้องอ่านจริงเท่านั้น

### เรื่องที่ 1 · panel ทับกัน — **ก่อนหน้านี้ไม่มีโค้ดกันเลย**

`panelRect` ขยายกล่องแนวตั้งออกจากจุดกึ่งกลาง ซึ่งเปลี่ยน “เกือบชนกัน” ให้เป็น “ทับกัน” ทันทีบนหน้าที่คอลัมน์อยู่ชิดกัน
สองข้อความทับกัน = อ่านไม่ได้ทั้งคู่ และผู้อ่านไม่มีทางรู้ว่าคำไหนของใคร

`core/panel-layout.ts` วาง panel ทีละอันตามลำดับอ่าน · **เลื่อนก่อน หดทีหลัง** เพราะการเลื่อนไม่เสียอะไรเลย (ยังคลุมหมึกของตัวเองอยู่)
แต่ละอันต้องหลบ **panel ที่วางเสร็จแล้ว** ของตัวก่อนหน้า และ **กล่องหมึก (anchor)** ของตัวที่ยังไม่ได้วาง

> **สิ่งที่รับประกันได้:** ถ้ากล่องที่ detector ให้มาไม่ทับกัน → **ผลลัพธ์ไม่ทับกันแน่นอน**
> พิสูจน์ได้เพราะทุก panel ย่อกลับมาเท่า anchor ตัวเองได้เสมอ ดังนั้น “ทุกอันเท่า anchor” เป็นคำตอบที่ถูกต้องอยู่แล้วคำตอบหนึ่ง
> ถ้ากล่องหมึก**ทับกันเอง** ไม่มีสี่เหลี่ยมชุดไหนคลุมหมึกครบโดยไม่ทับกันได้ → ย่อเหลือ anchor แล้ว**ติดธง `crowded`** แทนที่จะแอบเปิดตัวหนังสือญี่ปุ่นออกมา

### เรื่องที่ 2 · ให้โมเดลเสนอ ไม่ใช่ให้โมเดลสั่ง

“3 คอลัมน์นี้เป็นประโยคเดียวหรือ 3 ประโยค” เป็นคำถามเรื่อง**ภาษา** ไม่ใช่เรื่องพิกัด · ไม่มี threshold ไหนตอบถูกทุกหน้า
โมเดลได้รับ crop ทั้งหน้าใน 1 คำขออยู่แล้วและอ่านมันครบแล้ว → **มันเป็นฝ่ายเดียวในระบบที่รู้**

แต่ **การรวมเกินคือความพังที่แพงที่สุดของโปรเจกต์นี้** (สองคนพูดคนละบอลลูน พอรวมกันจะได้คำแปลเดียวที่ฟังดูมั่นใจและผิด โดยผู้อ่านมองไม่ออก)
จึงเป็น **ข้อเสนอ** ที่ต้องผ่านการตรวจพิกัดอีกชั้น (`core/merge-proposals.ts`) ทุกข้อ:

| ด่าน | ค่า | มาจากไหน |
|---|---|---|
| ใกล้กันอยู่แล้ว (ทั้งแกนอ่านและแกนขวาง) | `maxPerpGapRatio × 2` = **3 glyph** สำหรับแนวตั้ง | เป็นการ**ผ่อน**ค่าที่ `GROUPING_DEFAULTS` ใช้อยู่ 2 เท่า ไม่ใช่เลขใหม่ · ระยะระหว่างบอลลูนสองใบมีเส้นขอบ + ที่ว่าง กว้างกว่านี้หลาย glyph |
| ต้องเป็น**เศษ** ไม่ใช่ bubble ทั้งใบ | กว้างข้ามแกน ≤ **2.5 glyph** | ด่านที่กันเคส “สองคนพูด” **ตรงๆ** ไม่ใช่กันด้วยความบังเอิญของ threshold |
| ขนาดตัวอักษรพอกัน | `maxSizeRatio` = 1.7 (ค่าเดียวกับ grouping ปกติ) | กันเสียงประกอบถูกดูดเข้าไปในบทพูด |
| กล่องรวมต้องไม่พองเกิน | อัตราส่วน ≤ 3.5 · กินภาพเพิ่ม ≤ **5% ของหน้า** · กล่องรวม ≤ 30% ของหน้า | **อัตราส่วนอย่างเดียวใช้ไม่ได้**: คอลัมน์สองอันที่เยื้องกันจะได้ ≥ 2 เสมอโดยธรรมชาติ ตัวที่มีฟันจริงคือ “กินภาพเพิ่มกี่ %” |
| สมาชิก | 2–6 กล่อง · กล่องหนึ่งเป็นของข้อเสนอแรกที่อ้างสิทธิ์เท่านั้น | ผลลัพธ์เดิมสำหรับคำตอบเดิม |

**ราคาของการปฏิเสธ = 0** เพราะ prompt ยังบังคับให้ตอบ 1 item ต่อ 1 crop เหมือนเดิมเสมอ — ปฏิเสธแล้วได้พฤติกรรมเดิมเป๊ะ

**เก็บผลการรวมลงแคชพร้อมผลอ่าน (key = imageHash)** เพราะโมเดลไม่ deterministic · ถ้าไม่เก็บ หน้าเดียวกันอาจรวมคนละแบบในการอ่านครั้งถัดไป แล้วบั๊กจะ reproduce ไม่ได้เลย
**สวิตช์ปิดมีตั้งแต่วันแรก** — `translation.modelGrouping` + checkbox ในหน้าตั้งค่า · เป็นฟิลด์ optional (ไม่มี = เปิด) จึง**ไม่ต้อง migrate** ใคร

### 🔴 D-033 ตอบถูก แต่ถามคำถามที่แคบไป — เจ้าของเป็นคนชี้

D-033 ถามว่า “**เดา** URL ของหน้า n+1 จากหน้า n ได้ไหม” แล้วตอบว่าไม่ได้ทั้ง luscious และ e-hentai · **ข้อนั้นยังจริงทุกตัวอักษร**
แต่ในรายงานเดียวกันนั้นบันทึกไว้เองแล้วว่า:

- **luscious** mount `.picture-row` เป็น *หน้าต่าง* — บางอันยัง decode ไม่เสร็จ แต่ **มี `src` จริงอยู่ในนั้นแล้ว**
- **e-hentai MPV** เก็บหน้าต่างของรูปที่โหลดแล้ว และ `window.imagelist` มี URL จริงของหน้าที่อยู่ในหน้าต่างนั้นพอดี

**URL ของหน้าถัดๆ ไปไม่ได้ “ไม่รู้” — เว็บบอกไว้แล้ว** · การอ่านรายการที่เว็บพิมพ์ไว้เองดีกว่าการเดารูปแบบทุกทาง:
ไม่มี 404 · ไม่ยิงไปยัง URL ที่อาจไม่มีอยู่ · ไม่ต้องดูแล pattern รายเว็บ · และไม่ต้อง `MAX_CONSECUTIVE_MISSES` มาคอยกันความเสียหาย

ทั้งสองเว็บให้แค่ *หน้าต่าง* ไม่ใช่ทั้งเล่ม ซึ่งพอ — lookahead ต้องการแค่ไม่กี่หน้าอยู่แล้ว (ค่า default = 3)

### สิ่งที่วัดได้จริง (CDP · Edge 151 · โปรไฟล์ `D:\mt-profile` · viewport 768 px · 2026-08-16)

| | luscious (`my-fav_606101`) | e-hentai MPV (`4123216`) |
|---|---|---|
| ที่มาของเลขหน้า | `data-row-key="row-{i}-{ULID}"` บน **พ่อ**ของ `.picture-row` (0-based, ทั้งอัลบั้ม) | `id="imgsrc_{n}"` (1-based, ทั้งเล่ม) |
| หน้าต่างที่ mount | 3 แถวตอนบนสุด · 4–5 แถวหลังจากนั้น | 3 รูปที่โหลดแล้ว (ตอนวัด) |
| **หน้าที่อยู่*ข้างหน้า*ผู้อ่าน** | scrollY 6,600 → **1** · 10,000 → **2** · 13,400 → **2** | scrollY 0 → **2** |
| ตำแหน่งไกลสุดที่ได้ | +3,264 px และ +3,475 px (≈ 4.3 จอ) | +3,709 px (≈ 4.8 จอ) |
| แถวที่ยังไม่ decode แต่มี `src` แล้ว | **มีทุกครั้ง** (`loading="lazy"`, `complete=false`) | ไม่มี — MPV โหลดจริงก่อนจึงใส่ `<img>` |
| จำนวนหน้าทั้งเล่มจาก DOM | **ไม่มี** (virtualiser บอกแค่ความสูงรวม 221,842 px) | **`.mimg` = 26 ตัว ครบตั้งแต่เฟรมแรก** |
| URL เดาได้ไหม | ❌ ULID ต่อรูป | ❌ Hath node คนละโฮสต์ + keystamp เซ็นชื่อ |

**ระยะที่ IntersectionObserver เอื้อมถึงคือ `rootMargin` 2 จอล่าง = top < 2,304 px** · ของที่ published ให้เพิ่มจึงมี 2 อย่าง:
หน้าที่อยู่**เลย 2,304 px ออกไป** (ตัวที่ observer ยังไม่แตะ) และหน้าที่ **`src` มาแล้วแต่เบราว์เซอร์ยังไม่ยอมโหลด** (luscious lazy — ทางปกติได้แต่นั่งรอใน `pendingLoad`)

> ข้อเท็จจริงที่ต้องบอกตรงๆ: **ได้เพิ่มประมาณ 1–2 หน้า ไม่ใช่ทั้งบท** เพราะเว็บทั้งคู่ mount แค่หน้าต่าง
> และตอนวัด MPV หยุดโหลดอยู่ที่ 3 รูปไม่ขยายต่อ — ถ้าเจ้าของตั้ง lookahead ไว้ลึก เว็บสองอันนี้จะไม่ใช้ความลึกนั้น

### 3 อย่างที่ตัดสินใจเองในส่วนนี้ — ค้านได้

1. **“ข้างหน้า” วัดจากขอบล่างของ viewport (`top >= innerHeight`) ไม่ใช่จาก `?index=`**
   luscious มี `?index=` ก็จริง แต่วัดแล้ว **ตอนที่ผู้อ่านอยู่ที่ row-4 URL ยังเขียนว่า `index=3`** (และ row-6 ↔ `index=5`) — คลาดไป 1 หน้าในทิศที่แย่ที่สุด
   ตำแหน่ง element กับ URL ของรูปมาจาก **การอ่าน DOM ครั้งเดียวกัน** จึงขัดกันเองไม่ได้ ต่างจาก URL ของหน้าเว็บ
2. **ทับกับ IntersectionObserver ได้ ไม่ถือว่าเสีย** — งานถูก key ด้วย URL อยู่แล้ว งานของ element จะ `adopt` ตัวที่วิ่งอยู่แทนที่จะยิงซ้ำ (มีมาตั้งแต่ D-027)
3. **URL ที่เว็บพิมพ์ให้ ถ้าพลาด ไม่นับเป็น “เดาผิด”** — `MAX_CONSECUTIVE_MISSES` ใช้กับ URL ที่เรา*เดา*เท่านั้น
   เพราะ URL ที่อ่านมาไม่ได้เป็นความคิดของเรา และหน้าถัดไปก็อ่านมาแยกต่างหาก ไม่ได้ derive จากหน้านี้ → หน้านี้พังไม่ได้แปลว่าหน้าหน้าพัง
   (keystamp ของ e-hentai หมดอายุรายไฟล์ ถ้านับรวมจะปิด prefetch ทั้งเล่มเพราะรูปเดียว) · ความเสียหายยังมีเพดาน: แต่ละหน้าถูกลองแค่ **ครั้งเดียว** เพราะ mark `covered` ก่อนยิง

### ต้นเหตุจริงข้อที่ 3 — ผูก “รอเน็ต” ไว้กับ “รัน ONNX”

งานหนึ่ง = detect 0.1–0.5 วิ + รอ Gemini 1.3–41 วิ · **97% คือรอเน็ต** แต่ทั้งก้อนถูก serialize
`maxConcurrentOcr: 1` เขียนไว้กัน ONNX (D-013 ถูกต้อง) แต่ไปคุมทั้ง round trip ด้วย

### สิ่งที่ทำ — 4 คันโยก + ตั้งค่าที่เจ้าของสั่ง

1. **แยก concurrency** — detect ยัง serialize (chain แยกใน `pipeline.ts`) · ทั้งงานวิ่งพร้อมกันได้ 4 · **กัน 1 ช่องไว้ให้หน้าที่ผู้อ่านเห็นเสมอ** การเดาแย่งไม่ได้
2. **แบ่งงานข้าม key** — เลือก key ที่ “ว่างเร็วที่สุด” เสมอกันเรียงตามลำดับผู้ใช้ · key 1 ยังถูกใช้จนเต็มก่อน (โควตารายวันยังไล่ทีละใบ) แต่พอเต็มนาทีแล้วไป key 2 ทันทีแทนที่จะรอ
3. **ตัวคุมจังหวะต่อ key** — sliding window เล็ง **14 ไม่ใช่ 15** เพราะนาฬิกาเป็นของ Google และคำขอค้างอยู่ 1.3–41 วิ · โดน 429 = เติม window ของ key นั้นเต็มทันที (เชื่อ API มากกว่าบัญชีเรา)
4. **หลายหน้าใน 1 คำขอ** (สูงสุด 3 หน้า / 24 crop / 3 MB) — **หน้าที่เห็นอยู่ไม่เคยรอ batch** ส่งทันทีและกวาดหน้าที่รออยู่ไปด้วย · หน้าที่ยังไม่ถึงตา (lookahead) รอได้ 700 ms · คลิกขวาส่งเดี่ยวเสมอ
5. **prefetch ลึกได้ถึง 200 หน้า** + ตัวเลือก “ทั้งตอน” · กฎมารยาทไม่ขยับ (ทีละคำขอ, ห่าง 0.5 วิ, หยุดเมื่อสลับแท็บ) · ลึกขึ้น = ไปไกลขึ้น ไม่ใช่ยิงถี่ขึ้น
6. **คลิกขวา = จริงจังเสมอ** — ขึ้นหัวคิวก่อนทุกอย่าง · ไม่ไป adopt งานที่วิ่งอยู่ · **force เสมอ** (เดิม force เฉพาะตอนที่เคย*สำเร็จ*มาก่อน ซึ่งกลับด้าน: หน้าที่เคย*พัง*ไม่เคยเข้า `done` จึงกดซ้ำแล้วได้ของเดิม)

### 🔴 วัดก่อนแก้ แล้วเจอว่าเพดาน 200 MB เดิม “ไม่เคยทำงาน” และไม่มีวันทำงาน

**แคชไม่ได้เก็บรูป** — `OcrRecord` เก็บแค่กรอบสี่เหลี่ยม + ตัวหนังสือ (`cache/db.ts`)
วัดด้วยหน้าญี่ปุ่นจริงขนาด 13 กล่อง บทพูดยาวๆ:

| | ขนาดต่อ record (`approxBytes`) |
|---|---|
| หน้ามังงะ 13 กล่อง | **3,960 bytes ≈ 4 KB** |
| ประโยคที่แปลแล้ว 1 บรรทัด | **388 bytes** |

→ เพดาน 200 MB = **ประมาณ 52,000 หน้า** · เจ้าของอ่านวันละ 200 หน้าติดกัน **260 วัน** ถึงจะแตะ
แปลว่าโค้ด `evictIfNeeded()` ที่มีอยู่ **ไม่เคยลบอะไรเลยสักครั้งตั้งแต่เขียนมา** และช่อง “x.x MB” ในหน้าตั้งค่าก็แสดง 0.1 MB ตลอด

> **ข้อนี้ขัดกับสมมุติฐานในใบสั่งงาน** ที่เขียนว่า “หน้า MangaDex ~2.5 MB · imhentai เล็กกว่ามาก ดังนั้นจำนวนหน้าที่ไม่จำกัด = ดิสก์ที่ไม่จำกัด”
> 2.5 MB คือขนาด**ไฟล์รูป** ซึ่ง**ไม่ได้ถูกเก็บลงแคชเลย** (มันอยู่ใน HTTP cache ของเบราว์เซอร์ ซึ่งเราไม่ได้เป็นเจ้าของ)
> **ยังเก็บเพดาน byte ไว้ตามที่สั่ง** — แต่ขอบันทึกไว้ตรงๆ ว่ามันเป็นตัวกันเผื่อรูปแบบ record เปลี่ยนในอนาคต ไม่ใช่ตัวที่ผูกจริงในวันนี้

### ที่ทำ

**`cache: { maxPages, maxBytes }` ใน settings v4** · ตรรกะทั้งหมดอยู่ใน `core/cache-budget.ts` เป็น pure function + **26 tests**
`stores.ts` เหลือหน้าที่ย้าย record อย่างเดียว

| ค่า | ตั้งไว้ | ทำไม |
|---|---|---|
| `maxPages` default | **200 หน้า** | ครอบตอนหนึ่งของ MangaDex (20–45) และเล่มหนึ่งของ imhentai ทั้งเล่ม → คนที่ไม่แตะอะไรเลย**ไม่มีวันเจอการลบ** · ราคา ≈ **0.8 MB** |
| `maxPages` ต่ำสุด | **11** = `MAX_LOOKAHEAD + 1` | ดูหัวข้อถัดไป |
| `maxPages` สูงสุด | 2000 | ทั้งเพดาน ≈ 8 MB — “เก็บหมด” ถูกจนไม่ต้องคิด ของแพงในโปรเจกต์นี้คือ**คำขอ** ไม่ใช่ดิสก์ |
| `maxBytes` default | **200 MB (เท่าเดิม)** | ไม่เปลี่ยนพฤติกรรมที่ใช้อยู่ · เลือกได้ 20–2000 MB |

**ปุ่มลัดในหน้าตั้งค่า:** `40 หน้า` · `ทั้งตอน (60)` · `ทั้งเล่ม (200)` · `เก็บหมด (2000)` + ช่องพิมพ์เลขเอง
**แสดงการใช้งาน 2 หน่วยพร้อมกัน** ทั้งในหน้าตั้งค่าและใน “ตรวจสอบระบบ”: `37 / 200 หน้า · 0.15 / 200 MB · 481 ประโยค` · ปุ่มล้างอยู่ครบเหมือนเดิม

### 🔴 จุดที่ setting สองตัวชนกัน — กันด้วยพื้น ไม่ใช่ด้วยคำเตือน

**ถ้าแคชเล็กกว่า “อ่านล่วงหน้า” หน้าที่ prefetch ไว้จะถูกลบทิ้งก่อนผู้อ่านจะไปถึง** → เสียทั้งคำขอ โควตา และรอบ GPU ฟรีๆ แล้วผู้อ่านยังเห็น “กำลังอ่านภาพ…” บนหน้าที่ระบบแปลเสร็จไปแล้ว

เลือก**ทำให้ตั้งผิดไม่ได้** แทนการเตือน: `MIN_CACHE_PAGES = MAX_LOOKAHEAD + 1 = 11` เป็นพื้นตายตัว
lookahead มีเพดานที่ 10 อยู่แล้ว (`clampLookahead`) ดังนั้น **ไม่มีคู่ค่าไหนที่ขัดกันได้เลย** โดยไม่ต้องให้ไฟล์สองไฟล์อ่านค่าของกันและกัน
(หน้าตั้งค่ายังพิมพ์ค่า lookahead ปัจจุบันไว้ข้างๆ ให้เห็นด้วยตา)

> **ไม่ได้แตะ prefetch depth เลย** ตามที่สั่ง — `core/prefetch.ts` ไม่ถูกแก้ · `cache-budget.ts` แค่ `import { MAX_LOOKAHEAD }` มาอ่านค่าคงที่ตัวเดียว

### เปลี่ยนพฤติกรรมการลบ 2 อย่าง (ไม่ได้สั่ง — ค้านได้)

**1. ไม่เหลือ headroom แล้ว** — เดิมเกิน 200 MB จะลบลงไปถึง 160 MB (80%)
ถ้าคงไว้ “40 หน้า” จะแปลว่า 32 หน้าจริงๆ ซึ่งเป็นการโกหกตัวเลขที่ผู้อ่านพิมพ์เอง · ตอนนี้ลบให้พอดีเป๊ะ = ลบทีละ 1 record ต่อหน้าใหม่ ซึ่งถูกกว่าการสแกนที่จ่ายอยู่แล้วมาก

**2. ถ้าลบ OCR หมดแล้วยังเกินเพดาน byte → ลบ translation ต่อ (เก่าสุดก่อน)**
เดิม “ลบเฉพาะ ocr store” — แต่ตัวนับ byte รวม**ทั้งสอง store** ส่วน translation store **ไม่มีเพดานของตัวเองและโตไปเรื่อยๆ ตลอดอายุการติดตั้ง**
ถ้าวันหนึ่ง translation ดันเกินเพดานเอง ผลของโค้ดเดิมคือ **ลบผลอ่านภาพทิ้งทั้งหมด (ครึ่งที่แพงที่สุด) แล้วก็ยังเกินอยู่ ทำซ้ำทุกหน้าไปตลอด**
ตอนนี้ translation เป็นทางเลือกสุดท้ายจริงๆ (ต้องไม่เหลือ OCR ให้ลบแล้วเท่านั้น) และมี `log.warn` บอกว่าเพดานถูกตั้งต่ำเกินไป

### migration v3 → v4

ไม่มีอะไรต้องย้าย — งบเดิมเป็น **ค่าคงที่ในโค้ด ไม่เคยถูกเก็บลง storage** record เก่าจึงแค่ได้ค่า default เพิ่มเข้ามา
**ความเสี่ยงจริงของ migration แบบ “เพิ่มฟิลด์เฉยๆ” ไม่ใช่ฟิลด์ใหม่ แต่คือการ bump version แล้วพารายการอื่นหายไปด้วย**
เจ้าของกำลังใช้ v3 อยู่ตอนนี้พร้อม key จริงและรายการเว็บจริง จึงเขียนเทสต์จับตรงนั้นโดยเฉพาะ (key + `autoSites` + `perSet` ต้องรอด) · gate ของ migration เดิมสองตัวใช้ `>= 2` / `>= 3` จึงยังทำงานถูกเมื่อ version เป็น 4
**เทสต์รวม 235 → 267** · `tsc --noEmit` ผ่าน

### ที่ยังทำไม่ได้ — “ทั้งตอน” เป็นตัวเลขที่เดา ไม่ใช่ตัวเลขที่วัด

site profile รู้ความยาวเล่มจริง (`total(doc)` อ่าน `<input id="pages">` ของ imhentai) **แต่มันอยู่ใน content script ส่วนงบแคชถูกบังคับใช้ใน service worker**
การต่อสายให้ SW รู้ความยาวเล่มต้องแก้ `entrypoints/content.ts` ซึ่งงานนี้ไม่ได้เป็นเจ้าของ (มี agent อีกตัวถืออยู่)
ปุ่ม “ทั้งตอน (60)” จึงเป็นเลขที่**ตั้งให้ใหญ่กว่าตอนไหนๆ** ไม่ใช่เลขที่อ่านมาจากเว็บ · ถ้าอยากได้ของจริง ทำทีหลังได้ในงานเดียวที่แตะทั้งสองฝั่ง

### 🟡 ที่ยังไม่ได้พิสูจน์

พิสูจน์ด้วย unit test + การอ่านชั้น storage เท่านั้น **ไม่ได้เปิดเบราว์เซอร์** (ตามที่สั่ง — profile ที่ล็อกอินอยู่มีตัวเดียวและ agent อีกตัวใช้อยู่)
สิ่งที่ยังไม่เห็นกับตา: หน้าตั้งค่าเรนเดอร์จริง และการลบเกิดขึ้นจริงบน IndexedDB จริง
(ตัวที่กันไว้: `planEviction` ถูกเทสต์ 26 เคสรวมเคสขอบ ส่วน `stores.ts` เหลือแค่ “ลบตาม key ที่แผนบอก”)

**ย้อนกลับ:** ง่าย — ถ้าอยากได้พฤติกรรมเดิมเป๊ะ ตั้ง `maxPages = 2000` (สูงสุด) แล้วเหลือแต่เพดาน byte ทำงานเหมือนเดิม
ถ้าอยากลบทั้งฟีเจอร์: schema เป็น v4 แล้วและมี migration ต้องเขียน migration ย้อนอีกชุด แต่ฟิลด์ที่เพิ่มไม่มีใครอื่นอ้างถึงนอกจาก `cache-budget.ts` กับหน้าตั้งค่า

### กติกาที่ยึด: ไม่แน่ใจ = ไม่แปล

“ไม่มีรูปไหนครองจอ” · “ยังไม่มีรูปไหนถูกวางบนหน้า” · “จอไม่มีขนาด” → **ตอบว่าหน้ารายการทั้งหมด**
ผิดสองแบบราคาไม่เท่ากัน: แปลหน้ารายการ = เสียโควตา + บังภาพปก · ไม่แปลหน้าที่ควรแปล = คลิกขวาเอง

**กั้นเฉพาะ auto** — คลิกขวา “แปลรูปนี้” ยังทำงานทุกที่รวมหน้ารายการ (`enqueue(img, manual=true)` ข้าม gate)

## D-029 · **แปลอัตโนมัติแยกตาม hostname** · ตอนอัปเกรดให้เปิดค้างไว้เฉพาะเว็บที่มี site profile
**2026-08-15 · `extension/src/core/site-scope.ts` (ใหม่), `shared/settings.ts`, `entrypoints/content.ts`, `popup/`, `options/`, `content/overlay/overlay.ts`**

เจ้าของแจ้งว่า เปิดแปลอัตโนมัติไว้อ่านมังงะ แล้วไปเปิดเว็บอื่นมันก็แปลด้วย — `autoTranslate` เป็น boolean ตัวเดียวทั้งเบราว์เซอร์ ทุกแท็บที่ไม่เกี่ยวจึงกินโควตาจาก 1,000 ครั้ง/วัน

**เปลี่ยนเป็น `autoSites: string[]`** = รายชื่อ hostname ที่**เปิด** · ไม่อยู่ในรายการ = ปิด ไม่มีสถานะที่สาม
`enabled` **ยังเป็น global เหมือนเดิม** เพราะ “หยุดทุกอย่าง” ต้องกดได้โดยไม่ต้องรู้ก่อนว่าตอนนี้อยู่เว็บอะไร

**คีย์เป็น hostname ไม่ใช่ URL** — ถ้าจำเป็น URL จะลืมทุกครั้งที่เปลี่ยนหน้าในเล่มเดียวกัน ซึ่งแย่กว่าไม่จำเลย
ตัด `www.` นำหน้าออก (`www.mangadex.org` = `mangadex.org` เว็บเดียวกัน) แต่**ไม่ตัด subdomain อื่น** และ**ไม่ match แบบ suffix** — `forum.imhentai.xxx` ถือเป็นคนละเว็บ เพราะการ match ท้าย domain คือวิธีที่สวิตช์ตัวเดียวเงียบๆ ครอบทั้งบริษัท

### การ migrate คือส่วนที่ต้องระวัง (v2 → v3)

สองคำตอบที่นึกออกก่อนใช้ไม่ได้ทั้งคู่:

| ทางเลือก | ทำไมไม่เอา |
|---|---|
| ปิดทุกเว็บ | เจ้าของอัปเดตแล้วเปิดเว็บมังงะ **เงียบสนิทโดยไม่มีอะไรบอกว่าทำไม** — พังของที่ใช้อยู่ |
| เปิดทุกเว็บ | คือบั๊กที่ให้มาแก้ พาข้ามมาทั้งดุ้น |

**ที่เลือก:** ถ้า `autoTranslate` เดิมเป็น `true` → เปิดค้างไว้เฉพาะ hostname ที่**มี site profile** (`mangadex.org`, `imhentai.xxx/.com/.net`) นอกนั้นปิด
เว็บพวกนั้นคือที่เดียวที่ฟีเจอร์นี้เคยเล็งไว้จริง การอ่านของเจ้าของจึงไม่สะดุด และแท็บอื่นหยุดกินโควตาในก้าวเดียวกัน
`imhentai` มีหลาย TLD และ `match()` ครอบทั้งหมด แต่ migration ต้องการชื่อจริง — **ใส่ทั้ง 3 ตัวที่รู้จัก** เพราะถ้าเดาผิดตัวเว็บนั้นจะเงียบ ส่วนแถวที่ไม่ได้ใช้กดลบทิ้งได้ในคลิกเดียว

เงื่อนไขเดียวกับ migration ของ API key: **เช็คจาก `version` ที่เก็บไว้ ไม่ใช่เช็คว่ารายการว่าง** — หลัง migrate แล้ว “ว่าง” คือการตัดสินใจ (ผู้ใช้ลบเว็บสุดท้ายทิ้งเอง) ถ้า seed ซ้ำจะลบไม่ได้ตลอดกาล · และ **ลบฟิลด์ `autoTranslate` ทิ้ง** ไม่ให้เหลือ global เก่าค้างใน storage

## D-027 · หน้าที่ prefetch ไว้แล้วต้องขึ้น**ทันที** — จำ `URL → imageHash` ไว้ใช้ซ้ำ
**2026-08-15 · `extension/src/entrypoints/content.ts`, `core/prefetch.ts` (คอมเมนต์)**

เจ้าของแจ้งว่า “เปลี่ยนหน้าแล้วยังขึ้น *กำลังอ่านภาพ…* และยังต้องรอ” ทั้งที่ prefetch ทำไปแล้ว **วัดจริงที่ความเร็วอ่านจริง (กดเปลี่ยนหน้าทุก 2–4 วินาที) แล้วพบว่าเจ้าของพูดถูก**

| | ก่อนแก้ | หลังแก้ |
|---|---|---|
| เวลาจากกดเปลี่ยนหน้า → คำแปลขึ้น (median จาก 8 ครั้ง) | **1,155 ms** | **95 ms** |
| ช่วง | 647–2,660 ms | 77–3,302 ms |
| เห็นป้าย “กำลัง…” กี่ครั้งใน 8 ครั้ง | **7** | **2** |
| คำขอ Gemini ต่อหน้า | 1.00 | 1.00 |

> ตัวเลข **96 ms** ที่ [D-026](#) อ้างไว้ วัดตอนปล่อยให้ prefetch ทำเสร็จก่อนแล้วค่อยกด — ซึ่งไม่ใช่วิธีที่คนอ่านจริง ตัวเลขที่ควรเชื่อคือ 1,155 ms

**ต้นเหตุ:** ถึงจะ prefetch หน้าถัดไปครบทั้ง pipeline แล้ว พอผู้ใช้กดมาถึงจริง เรายัง**เดินครบรอบใหม่ทั้งรอบ** — content script → service worker → ดาวน์โหลด bytes ซ้ำ → sha256 ใหม่ → อ่าน IndexedDB สองสโตร์ → ส่งกลับ — ทั้งหมดเพื่อ**ค้นหา hash ที่ worker เพิ่งบอกเราไปเมื่อ 5 วินาทีก่อน** ค่าใช้จ่าย 0 คำขอ Gemini ก็จริง แต่เสียเวลาราว 1 วินาทีทุกหน้า

**แก้:** เก็บ `Map<imageUrl, imageHash>` ใน content script ทุกครั้งที่ได้ `RESULT` (คีย์คือ URL ที่ worker ดึงมาจริง — URL ที่เดาไว้สำหรับ prefetch หรือ `currentSrc` สำหรับงานปกติ) พอ `src` ใหม่ตรงกับ URL ที่รู้จักและ overlay ยังถือผลนั้นอยู่ → **วาดเลย ไม่ต้องคุยกับ worker**

**ข้อสมมุติที่ยอมรับ (จุดที่ควรค้านถ้าไม่เห็นด้วย):** URL เดียวกันให้ bytes ชุดเดิมตลอดช่วงที่หน้าเว็บนี้เปิดอยู่
เป็นข้อสมมุติเดียวกับที่ HTTP cache ของเบราว์เซอร์ใช้อยู่แล้ว (รูปที่ผู้ใช้เห็นบนจอ ณ ตอนนั้นก็มาจากแคชตัวนั้น) · map ตายพร้อม content script จึงข้ามเซสชันไม่ได้ · ใส่เฉพาะ URL ที่เราดึงมาเองเท่านั้น · การกด “แปลรูปนี้” เองยังข้าม map เสมอ

**พิสูจน์ว่าไม่ทำให้คำแปลค้างผิดหน้า:** เดินหน้า 1→9 แล้วถอยกลับ 9→1 รวม 16 ครั้ง — **src 9 แบบ ↔ hash 9 แบบ ไม่ซ้ำและไม่สลับกันเลย ผิดพลาด 0 ครั้ง** · ขากลับใช้ **61–73 ms ทุกหน้า** และ **0 คำขอเพิ่ม**

**ราคาที่จ่าย:** หน้าที่วาดจาก map จะไม่ได้อัปเดต `recentContext` ใน worker (บทพูดหน้าก่อนที่ส่งให้ Gemini เพื่อความต่อเนื่อง) — แต่หน้านั้นเคยวิ่งผ่าน pipeline ตอน prefetch แล้วและอัปเดตไปรอบหนึ่งแล้ว จะต่างแค่**ลำดับ** ซึ่ง context ตัวนี้เป็น best-effort อยู่แล้วตามที่เขียนไว้ใน `pipeline.ts`

**แก้คอมเมนต์ที่โกหกไปด้วย:** `core/prefetch.ts` เขียนว่า worker รันงานเดา “ในเลนแยกที่หลบให้ผู้อ่าน (ดู `entrypoints/background.ts`)` — **เลนนั้นไม่มีอยู่จริง** `background.ts` มีคิวเดียว (`enqueue`) งานของผู้อ่านที่มาถึงตอนงานเดากำลังวิ่งจะต่อท้ายมันจริงๆ
วัดแล้วบน imhentai ไม่เสียหาย เพราะงานเดาที่วิ่งอยู่มักคือหน้าที่ผู้ใช้กำลังจะเปิดพอดี (เห็น `adopted prefetch` 5 ครั้งใน 16 ครั้ง) **แต่ถ้าผู้ใช้กระโดดไปหน้าที่ไม่ได้เดาไว้ จะต้องรออีก 1 งาน** — ยังไม่ได้แก้ ปล่อยไว้เป็นเลนเดียวตามเดิม เพราะยังวัดไม่เจอว่ามันทำร้ายใคร

**ยังไม่ได้พิสูจน์:** MangaDex — วันที่แก้นี้ `mangadex.org` ต่อไม่ติดจากเครื่องนี้เลย (`ERR_CONNECTION_TIMED_OUT`) เหตุผลที่คิดว่าปลอดภัยคือรูป MangaDex เป็น `blob:` ซึ่งเป็น URL ใหม่ทุกก้อน map จึงไม่มีทางชนกัน — แต่นั่นคือการวิเคราะห์ ไม่ใช่การวัด

**ย้อนกลับ:** ง่ายมาก — ลบบล็อก `hashOfUrl` ใน `enqueue()` ออก แล้วพฤติกรรมกลับไปเป็นเดิมทุกอย่าง

## D-026 · prefetch ยิงทั้ง pipeline ไม่ใช่แค่ warm รูป · เดา URL จาก**รูปหน้าปัจจุบัน** ไม่ใช่จากหน้า HTML
**2026-08-15 · `extension/src/core/prefetch.ts`, `core/page-url.ts`, `content/site-profiles.ts`, `entrypoints/content.ts`**

D-014 เลื่อน B7 ไว้เพราะ "ยิงเซิร์ฟเวอร์เขาล่วงหน้าต้องทำให้ถูกกติกา" — รอบนี้ทำแล้ว มี 3 การตัดสินใจย่อยที่ไม่ได้ถูกสั่งไว้

**1. prefetch = รัน pipeline เต็ม (ดึงรูป + detect + Gemini) ไม่ใช่แค่ดึงรูปมา warm cache ของเบราว์เซอร์**
เพราะจุดประสงค์คือ "กดหน้าถัดไปแล้วคำแปลขึ้นทันที" การ warm แค่ไฟล์รูปประหยัดแค่ ~200 ms จาก 3 วินาที ซึ่งไม่ตอบโจทย์เลย
**ราคาที่จ่าย = 0 คำขอเพิ่ม** ถ้าอ่านจนจบ (1 หน้า = 1 คำขอ เท่าเดิม แค่จ่ายก่อน) · **จะเสียเปล่าเมื่อเลิกอ่านกลางคัน** — วัดจริงในเทสต์: อ่าน 5 หน้า ใช้ 5 คำขอพอดี ไม่มีซ้ำ

**2. เดา URL หน้าถัดไปจาก URL ของ*รูป*ที่แสดงอยู่ (`.../1.webp` → `.../2.webp`) ไม่ใช่ไปโหลด `/view/{id}/{n}/` มาแกะ**
งานที่สั่งเขียนว่า "imhentai's `/view/{id}/{n}/` pattern" แต่ URL นั้นเป็นหน้า HTML ไม่ใช่รูป ถ้าเดินทางนั้นต้อง**ยิงเพิ่มอีก 1 คำขอต่อหน้า**เพื่อโหลด HTML (พร้อมสคริปต์โฆษณาทั้งชุด) แล้วมาแกะหา `#gimg` — คือรบกวนเซิร์ฟเวอร์เขา 2 เท่าเพื่อให้ได้ข้อมูลที่รูปในมือบอกอยู่แล้ว
วัดจากเว็บจริง: `#gimg` = `https://m10.imhentai.xxx/029/yco3vdf5wj/1.webp` และหน้ามี `<input id="pages" value="9">` บอกความยาวเล่ม → รู้ทั้ง URL ถัดไปและจุดจบเล่มโดยไม่ต้องขออะไรเพิ่มเลย

> **ข้อจำกัดที่ยอมรับ:** ถ้าเล่มไหนสลับนามสกุลไฟล์กลางเล่ม (เช่น `.webp` ปนกับ `.jpg`) การเดาจะได้ 404 — หน้านั้นจะไม่ถูก prefetch เฉยๆ แล้วไปแปลตอนกดจริง ไม่มี retry วน (ทำเครื่องหมาย covered ก่อนยิงเสมอ) ยังไม่เจอเคสนี้ในเล่มที่ทดสอบ

**3. เพิ่มเงื่อนไข `idle` ที่งานไม่ได้สั่ง** — ห้าม prefetch ขณะหน้าที่ผู้ใช้มองอยู่ยังทำไม่เสร็จ
เพราะ SW รันงานทีละงานเป็นคิว ถ้าปล่อยให้ prefetch แทรก หน้าที่ผู้ใช้กำลังรอจะไปต่อคิวหลังงานเดา ซึ่งกลับหัวกลับหางกับเจตนาของฟีเจอร์

**MangaDex ไม่ทำ** — ตามที่สั่ง profile ไม่มีช่อง `prefetch` เลย จึงไม่มีทางยิงคำขอเดาไปที่นั่นได้ (เขาสร้าง `blob:` ในโค้ดตัวเอง เดาไม่ได้จริงๆ) · เขียนเหตุผลไว้เป็นคอมเมนต์ใน profile ไม่ใช่แค่ในเอกสาร

**เพดานอยู่ที่การ "อ่านค่า" ไม่ใช่ตอนเซฟ** — `hydrate()` เรียก `clampLookahead()` ทุกครั้งที่โหลด settings ดังนั้นค่าที่ถูกแก้มือใน storage ก็ยกเพดานไม่ได้ · ค่าที่ไม่ใช่ตัวเลข (NaN/Infinity) ตกเป็น **0 = ปิด** ไม่ใช่ 10 เพราะ setting ที่พังไม่ควรกลายเป็นการยิงถี่ที่สุดที่อนุญาต

**วัดจริง (Chrome for Testing, imhentai 9 หน้า):** 1 คำขออ่านหน้าปัจจุบัน + 3 คำขอล่วงหน้าพอดี แล้วหยุด · ห่างกันน้อยสุด **1,749 ms** (เพดานคือ 500) · ไม่เคยเกิน **1 คำขอต่อวินาที** · กดหน้าถัดไปแล้วคำแปลขึ้นใน **96 ms** · สลับไปแท็บอื่น 20 วินาที = **0 คำขอ**

**ย้อนกลับ:** ง่ายมาก — ตั้ง lookahead = 0 ในหน้าตั้งค่า หรือลบช่อง `prefetch` ออกจาก profile

## D-025 · **ไม่ล้าง overlay ทั้งหมดเมื่อ URL เปลี่ยน** — ตรวจทีละอันแทน
**2026-08-15 · `extension/src/entrypoints/content.ts`, `content/overlay/overlay.ts`**

โค้ดเดิมเจอ `pushState`/`popstate` แล้ว `overlay.clearAll()` ทันที ด้วยเหตุผลที่ฟังดูถูก ("URL เปลี่ยน = เปลี่ยนหน้า อะไรที่วาดอยู่เชื่อไม่ได้")

**มันผิดบน MangaDex** ซึ่งเปลี่ยนหน้าโดย**สลับว่า element ไหนถูกแสดง** ไม่ใช่สลับ `src` — หน้าที่แล้วถูกย่อเหลือ 0×0 หน้าถัดไปถูกขยายขึ้นมา ทั้งคู่เป็น element คนละตัวที่มีคำแปลถูกต้องของตัวเองอยู่แล้ว
ผลของ `clearAll()` คือ **คำแปลหายทุกครั้งที่กดหน้าถัดไป และไม่กลับมาอีกเลย** เพราะ element นั้นถูกทำเครื่องหมาย `done` ไปแล้ว `enqueue` จึงตัดทิ้งทันที ผู้ใช้จะเห็นเป็น "แปลได้หน้าเดียวต่อการรีเฟรช 1 ครั้ง"

**แทนที่ด้วยการตรวจ invariant ตัวจริง:** overlay ที่วาดอยู่ต้องตรงกับ bytes ที่อยู่ใน element นั้น ณ ตอนนี้ — `done.get(img) !== srcOf(img)` เมื่อไหร่ก็ถอดอันนั้นทิ้ง ไม่ยุ่งกับอันอื่น
บน imhentai ตัวที่จับการเปลี่ยนหน้าคือ MutationObserver บน `src` อยู่แล้ว (แม่นกว่า เพราะรู้ว่า element ไหน) `clearAll()` จึงไม่เคยจำเป็นตั้งแต่แรก

**ของแถมที่ต้องแก้พร้อมกัน — `ResizeObserver`:** overlay จัดตำแหน่งใหม่เฉพาะตอน `scroll`/`resize` แต่ MangaDex เปลี่ยนขนาด element โดยไม่มีทั้งสองอย่าง → หน้าที่ถูกแปลไว้ตอนยังอยู่ในช่อง preload (0×0) จะมี overlay ค้างขนาด 0 ตลอดไปหลังถูกแสดง

**พิสูจน์แล้วด้วยการวัดพิกัดจริง:** หลังกดหน้าถัดไป layer ของหน้า 2 ขยายเป็น `155,0 610×865` **ตรงกับ `getBoundingClientRect()` ของรูปเป๊ะ (dx=0)** และ layer ของหน้า 1 ยุบเป็น 0×0 — มี layer ขนาดจริงอยู่ **1 อันเท่านั้น** บนหน้าจอ

**ย้อนกลับ:** ง่าย

## D-024 · เปลี่ยนหน้า = **ยกเลิกงานที่ค้าง** ไม่ใช่ปล่อยให้จบแล้วเก็บเข้าแคช
**2026-08-15 · `extension/src/entrypoints/content.ts`, `entrypoints/background.ts`**

พอผู้ใช้กดหน้าถัดไปขณะที่หน้าเดิมยังแปลไม่เสร็จ ตอนนี้เราส่ง `CANCEL` แล้ว SW ก็ abort ทิ้ง (และข้ามงานที่ถูก abort ไปแล้วตอนถึงคิว)

**ทำไม:** โควตาฟรีนับ**จำนวนคำขอ 1,000/วัน** ไม่ใช่โทเคน คนที่กดผ่านๆ หา 10 หน้าจะเผาไป 10 คำขอโดยไม่ได้อ่านสักหน้า ทั้งที่รู้ตั้งแต่วินาทีที่กดแล้วว่าไม่ได้จะอ่าน

**ราคาที่จ่าย:** ถ้าผู้ใช้กดกลับมาหน้าเดิมทันที จะต้องเริ่มใหม่ — เห็นจริงในเทสต์ (เดินย้อนกลับ 5 หน้า มี 3 หน้าที่ถูกยกเลิกไปก่อนหน้าต้องแปลใหม่) รับได้ เพราะกรณี "เปลี่ยนใจกลับทันที" พบน้อยกว่ากรณี "เลื่อนหา"

**ย้อนกลับ:** ง่าย — ลบ `cancel()` ใน `enqueue` ออก 1 บรรทัด

## D-023 · หน่วยของงานคือ **(element, src ตอนเริ่ม)** ไม่ใช่ element · ตัวจุดชนวนคือ `load` ไม่ใช่ MutationObserver
**2026-08-15 · `extension/src/entrypoints/content.ts`, `content/scan.ts`**

ทุกการทดสอบก่อนหน้านี้รันตอน **auto-translate ปิด** ทั้งหมด พอเปิดจริงแล้ววัดบนเว็บจริง เจอว่าเส้นทางอัตโนมัติ — ซึ่งเป็นหัวใจของโปรเจกต์นี้ — **พังอยู่ 3 จุดพร้อมกัน**

**จุดที่ 1 — เปลี่ยนหน้าแล้วไม่แปลเลย (วัดได้: 60 วินาที 0 overlay)**
`enqueue()` ขึ้นต้นด้วย `if (!isLoaded(img)) return;` และ MutationObserver เรียกมันตอน `src` เพิ่งเปลี่ยน ซึ่ง ณ วินาทีนั้น `img.complete === false` **เสมอ** → return เงียบๆ ทุกครั้ง และไม่มีใครลองใหม่อีก
IntersectionObserver ก็ช่วยไม่ได้เพราะ element เดิม intersect อยู่แล้ว ไม่มี event ใหม่

**แก้: ใช้ `load` เป็นตัวจุดชนวน** — มันคือ event เดียวที่แปลว่า "bytes ที่อยู่บนจอตอนนี้คือชุดนี้" และมันครอบคลุมทั้งสองเคสพร้อมกัน: element ที่ยังโหลดไม่เสร็จตอน scan แรก (MangaDex ทุกครั้ง) และ element ที่ถูกสลับ `src` ไปหน้าใหม่ (imhentai ทุกครั้ง)

**จุดที่ 2 — ผลลัพธ์หน้าเก่าถูกวาดทับหน้าใหม่ (เห็นกับตา: หน้า 1 แสดง hash ของหน้า 5)**
งานผูกกับ element เฉยๆ พอ RESULT กลับมาก็ `attach(img, hash)` โดยไม่ถามว่า element นั้นยังแสดงรูปเดิมอยู่ไหม — บน imhentai ที่ใช้ `<img id="gimg">` ตัวเดียวทั้งเล่ม นี่คือบั๊กที่ **D-001 เขียนเตือนไว้ตั้งแต่วันแรก** แต่ถูกกันไว้แค่ครึ่งเดียว (ผูก overlay กับ hash ถูกแล้ว แต่ *การตัดสินใจว่าจะวาดไหม* ยังผูกกับ element)

**แก้: หน่วยของงานคือคู่ `(element, src ตอนเริ่มงาน)`** ถ้าตอนผลลัพธ์กลับมา `srcOf(img) !== job.src` → **ทิ้งผล ไม่วาด** แล้ว `enqueue` ตัวที่แสดงอยู่จริงแทน
(ยังเก็บ `setResult(hash, …)` ไว้เสมอ เพราะมันถูกของมันอยู่ — แค่ไม่ใช่ของหน้านี้)

**จุดที่ 3 — MangaDex scan แรกได้ 0 รูป**
`scanImages()` กรอง `isLoaded` ทิ้ง และ MangaDex ใส่ `<img>` ลง DOM ก่อน blob พร้อม → ตกรอบ · แล้วไม่มีอะไร rescan ตอนมันโหลดเสร็จ (childList ไม่ขยับแล้ว) → **ไม่เจอตลอดไป**
**แก้:** แยก `isPageCandidate()` ออกมาเป็นฟังก์ชันต่อ element และให้ observer เฝ้า element ที่ยัง**โหลดไม่เสร็จ**ด้วย แล้วค่อยตัดสินตอน `load`

**พ่วงมาด้วย: ปิดสวิตช์แล้วต้องหยุดจริง** — เดิม observer ยังทำงานอยู่แค่เช็ค flag · ตอนนี้ `io.disconnect()` + `mo.disconnect()` + ยกเลิกงานที่ค้าง + ล้าง overlay และกลับมาต่อเมื่อเปิดใหม่

**ไม่เลือก:**
- **poll ทุก 500 ms ว่ารูปเปลี่ยนไหม** — ง่ายกว่าและได้ผล แต่รันบนทุกแท็บตลอดเวลาเพื่อแก้ปัญหาที่มี event ตรงๆ อยู่แล้ว
- **ใส่ `isLoaded` guard แล้วให้ MutationObserver ลองซ้ำ** — ไม่มีอะไรมากระตุ้นให้ลองซ้ำ นั่นคือต้นเหตุเดิม
- **`decode()` แทน `load`** — ตอบช้ากว่าและไม่ยิงเมื่อรูปมาจากแคชในบางเคส

**วัดจริงหลังแก้ (Chrome for Testing):** imhentai หน้าแรก 3.3 วิ · เปลี่ยนหน้า 1.8–2.5 วิ · **สุ่มตรวจ 111 ครั้งระหว่างเปลี่ยนหน้า ไม่เจอ overlay ค้างเลยสักครั้ง** · MangaDex หน้าแรก 1.9 วิ โดยไม่ต้องแตะอะไร · เปิดแท็บใหม่หน้าเดิม = 0 คำขอ Gemini

**ย้อนกลับ:** ปานกลาง — เป็นการรื้อชั้น trigger ทั้งชั้น แต่ไม่แตะ pipeline/cache/overlay

## D-019 · ส่ง bytes ของรูปผ่าน **Cache Storage** ไม่ใช่ base64 ใน message
**2026-08-15 · `extension/src/shared/blob-bridge.ts`**

SW กับ offscreen อยู่ origin เดียวกัน (`chrome-extension://<id>`) จึงเห็น Cache Storage อันเดียวกัน → ฝ่ายส่ง `put()` ไว้แล้วส่งแค่ key ข้ามไป

**ทำไม:** กฎใน CLAUDE.md บอก “ห้ามส่ง base64 ใช้ ArrayBuffer transferable” แต่ **Chrome ไม่มี transferable ใน extension messaging** — `chrome.runtime.sendMessage` serialize แบบ JSON, ArrayBuffer ไปถึงปลายทางเป็น `{}` (crbug 248548 ยังไม่แก้) เจตนาของกฎคือ “อย่าคัดลอกก้อนใหญ่โดยไม่จำเป็น” ซึ่ง Cache Storage ตอบโจทย์นั้นได้ดีกว่า base64 ด้วยซ้ำ

**ยังเหลือ base64 อยู่ 1 ช่วง — content script → SW** เพราะ content script รันบน origin ของ**เว็บ** จึงเข้า Cache Storage ของ extension ไม่ได้เลย เป็นข้อจำกัดของแพลตฟอร์ม ไม่ใช่ทางเลือก (หน้า MangaDex 2.5 MB → string ~3.4 MB ครั้งเดียวต่อหน้า)

**ไม่เลือก:** base64 ทั้ง 2 ช่วง — คัดลอกก้อนใหญ่ 2 รอบโดยไม่จำเป็น · ให้ offscreen fetch เองทั้งหมด — ใช้กับ `blob:` ของ MangaDex ไม่ได้ และ SW ควรเป็นเจ้าของ policy การ fetch

**กันพัง:** ถ้า `caches.put()` ล้ม (quota/incognito) จะ fallback ไป base64 อัตโนมัติ — เสีย RAM ดีกว่าเสียทั้งหน้า

**ย้อนกลับ:** ง่าย อยู่ในไฟล์เดียว

`ms57rd/manga-ocr-base-ONNX` ส่ง `tokenizer.json` ขนาด 2.7 KB ที่มี vocab แค่ **5 token** (`[PAD] [UNK] [CLS] [SEP] [MASK]`) ทั้งที่ decoder ยิง id ในช่วง **6144 ตัวอักษรญี่ปุ่น** → ทุก id กลายเป็น `[UNK]` → `skip_special_tokens` ตัด `[UNK]` ทิ้ง → ได้ **สตริงว่าง**

นี่คือคำตอบของ "53 วินาทีแล้วได้ 0 block": โมเดลอ่านเสร็จแล้วแต่ **ถอดรหัสกลับเป็นตัวอักษรไม่ได้** ไม่มี error ไม่มี id เกินขอบเขต หน้าตาเหมือน crop ที่อ่านไม่ออกเป๊ะ — เลยรอดมาได้ทั้ง benchmark

แก้โดยดึง `vocab.txt` (6144 บรรทัด) จาก **kha-white/manga-ocr-base** ต้นฉบับ (Apache-2.0 เหมือนกัน โปรเจกต์เดียวกัน) มาเสียบเข้า tokenizer.json ใน `npm run models` — clone ใหม่ได้ของที่ใช้ได้เลย

**ชั้นที่ 2 — ตัว export เองก็พัง (แก้จากฝั่งเราไม่ได้ ❌)**
พอ vocab ถูกแล้ว โมเดล**อ่านออกมาเป็นภาษาญี่ปุ่นที่ดูดีแต่ไม่เกี่ยวกับภาพเลย** (`ん 娠 に 斥 候 表…` ทั้งที่ภาพเขียนว่า こんにちは)

ตัดตัวแปรออกทีละอย่างแล้ว:
- ❌ ไม่ใช่ quantization — โหลด **fp32 (460 MB)** มาลองแล้ว ได้ตัวอักษร**ชุดเดิมเป๊ะ**
- ❌ ไม่ใช่ backend — wasm กับ webgpu ให้ผลเหมือนกัน
- ❌ ไม่ใช่ preprocessing — `pixel_values` ออกมา `[1,3,224,224]` ช่วง -1..1 ถูกต้อง
- ❌ ไม่ใช่ beam search / KV-cache config — ปิดทั้งคู่แล้วไม่เปลี่ยน
- ✅ **ไฟล์ `decoder_model_merged.onnx` ไม่มี input `past_key_values` สักตัว** ทั้งที่ชื่อบอกว่า merged → ชื่อไฟล์โกหก graph ข้างในไม่ใช่ decoder ที่ transformers.js คิดว่ากำลังคุยด้วย

repo นี้เจอของเสีย **2 อย่างในไฟล์คนละไฟล์** (tokenizer stub + decoder mislabeled) และไม่ระบุ license ด้วยซ้ำ → เชื่อถือไม่ได้

**ทางออกที่ดีที่สุดถ้าจะรื้อฟื้น manga-ocr ในเบราว์เซอร์** (ไม่ได้ทำ เพราะไม่ใช่ทางหลักแล้วตาม D-005):
1. **export ONNX เอง** จาก `kha-white/manga-ocr-base` ด้วย `optimum-cli` — ได้ของที่ตรงกับ config แน่นอน เป็นทางที่ถูกต้องที่สุด
2. `ogkalu/manga-ocr-mobile` (Apache-2.0, encoder แค่ 17 MB) — แต่เป็น 3 ไฟล์แยก (`encoder`/`decoder_init`/`decoder_step`) ต้องเขียน generation loop เองด้วย ORT ตรงๆ transformers.js โหลดไม่ได้
3. Local Service (Python + manga-ocr ตัวจริง) — เลี่ยงปัญหา ONNX ทั้งหมด

**ผลย้อนกลับไปที่ ADR-001:** ตัวเลข **5.27 วิ/bubble วัดตอนที่โมเดลคืนสตริงว่าง** ทิศทางยังถูก (encoder อย่างเดียวก็หลายวินาทีแล้ว และ decode จริงจะช้ากว่านี้อีก) แต่ต้องถือเป็น **ขอบล่าง** ไม่ใช่ตัวเลขสรุป

**ทำอะไรเพิ่ม:** ติดป้าย 🔴 ใน dropdown ทั้ง 2 โหมด เพื่อไม่ให้ใครเผลอเอาไป benchmark ซ้ำ — ตอนนี้มันจะ**เรนเดอร์คำแปลมั่วแทนที่จะเงียบ** ซึ่งอันตรายกว่าตามกฎในโปรเจกต์

**ย้อนกลับ:** vocab fix ไม่ควรย้อน · ป้าย 🔴 เอาออกได้เมื่อมี export ที่ใช้ได้

## D-003 · คำนวณเรขาคณิตในพิกเซล ไม่ใช่ normalized
**2026-08-15 · `spike/src/types.ts`**

## หมายเหตุสำหรับ agent ที่มาทำต่อ

เมื่อคุณตัดสินใจอะไรที่**เจ้าของโปรเจกต์ไม่ได้สั่งไว้ชัดเจน** ให้เพิ่มรายการใหม่ไว้บนสุด ใช้เลข D-xxx ถัดไป และตอบให้ครบ 4 ข้อ:

1. ตัดสินใจอะไร (พร้อมไฟล์ที่เกี่ยว)
2. **ทำไม** — เหตุผลที่แท้จริง ไม่ใช่คำอธิบายว่าทำอะไร
3. ทางเลือกที่ไม่เลือก และทำไมถึงไม่เลือก
4. ย้อนกลับยากแค่ไหน (ง่าย / ปานกลาง / ยาก)

**อย่าบันทึก**การเลือกที่ชัดเจนอยู่แล้วหรือมีทางเดียว — log ที่มีแต่เรื่องไม่สำคัญจะไม่มีใครอ่าน
